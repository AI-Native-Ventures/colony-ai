# W10 Discovery, Services and Sales Implementation Plan

**Goal:** Implement the r19 desktop business journey from service definition and saved prospects through proposal acceptance and idempotent conversion.

**Architecture:** Store service and prospect state as signed Nostr business records scoped to the private business stream. Reuse existing proposal versions and conversion claims. Route all reads through the shared relay client, and keep provider search behind an explicit adapter boundary. OutScraper, Brave and Exa adapters are absent on the integration base, so production search remains a reported `NEEDS_API` dependency. E2E provider outcomes use the existing reference-workspace fixture only.

**Tech Stack:** Rust business-record validation in `buzz-core` and `buzz-relay`, TypeScript, React, TanStack Router, React Query, Tauri relay signer, Playwright.

## Acceptance gate

Pass when the signed service, prospect and proposal records render and update in the frozen r19 layouts; filters, qualification notes, saved state, duplicate warnings, pipeline stages and exact-version proposal revision work; accepted proposal retry resolves the original client, channel, work item and draft invoice; the W10 E2E flow passes at the 1440×900 and 1728×1117 logical viewports; and visual comparison confirms Manrope and r19 geometry. Provider-backed search is separately gated on provider APIs and must not make a real call during QA.

- `desktop/src/features/discovery/`: taxonomy, typed event parsing, prospect and service record operations, provider adapter boundary, query hooks and screens.

- `desktop/src/app/routes.ts` and `desktop/src/app/routes/`: register Discovery, campaign, Leads, lead detail, Pipeline, service, proposal list and proposal detail routes.
- `desktop/src/features/sidebar/ui/AppSidebar.tsx` and `AppSidebar.types.ts`: show only the W10 destinations that now have routes.
- `desktop/src/testing/e2eReferenceWorkspace.ts`: extend the existing reference fixture with W10 records and mock search outcomes.
- `desktop/tests/visual/reference-workspace-manifest.json`: add W10 route and viewport comparison cases.
- `desktop/tests/e2e/w10-discovery-sales.spec.ts`: bind workflow assertions to the production routes and fixture bridge.
- `crates/buzz-relay/src/handlers/business_records.rs`: extend the existing proposal conversion replay test to assert one receipt and one generated record set.

## Tasks

### 1. Add typed service and prospect business records

- Use existing `KIND_SERVICE_ACTION = 47002` and `KIND_SERVICE_HEAD = 30632`. They are already included in the registry, but service parsing and relay handling are missing.
- Add `KIND_PROSPECT_HEAD = 30644` and `KIND_PROSPECT_ACTION = 47034`; 30642 and 47031 are reserved for company goals.
- Add `ServiceRecord`, `ServiceAction`, `ServiceHead`, `ProspectEvidence`, `ProspectActivity`, `ProspectRecord`, `ProspectAction` and `ProspectHead` in `crates/buzz-core/src/business_records.rs`.
- Add the namespaced prospect `d` tag; use existing `business_d_tag` for service definitions. Bind prospect actions to both the business stream `h` tag and the prospect `d` tag.
- Parse each action in `parse_business_command`, reject unknown fields and invalid schema versions, and require bounded strings, nonnegative minor-unit amounts, valid currencies, allowed stages and HTTPS evidence URLs.
- Add table tests for valid creates, invalid stages, malformed evidence, unsupported versions, and cross-business tag mismatch.
- Run `CARGO_BUILD_JOBS=4 cargo test -p buzz-core business_records`.
- Commit with `git commit -s -m "feat: add W10 service and prospect record schemas"`.

### 2. Persist commands under business-channel authority

- Add service and prospect branches to `crates/buzz-relay/src/handlers/business_records.rs` using its existing `HeadWrite`, expected-head and transactional persist path. Add the preallocated service action to `is_business_command_kind` and `is_command_kind`.
- Require an active private business channel, authorized owner or admin for service changes, an authorized business member for prospect changes, and the command's exact expected head for updates.
- Create the identity `PartyHead` and `ProspectHead` in one transaction for a new prospect so proposal commands can reference the party without a torn two-event create.
- Preserve command replay behavior and return conflicts when the expected head is stale.
- Extend the relay handler tests for role denial, cross-community scoping, stale-head conflict, and command replay. These database-backed tests stay on hosted CI because local `buzz-postgres` is off limits.
- Commit with `git commit -s -m "feat: persist W10 service and prospect records"`.
