# Factory run preview and pull request records

Status: Phase 2 contract for FACTORY-1. Schema version: `1`.

## Storage boundary

The native Factory runtime remains the source of truth for local run execution,
transcripts, working copies, and cancellation. Preview and pull request metadata
live in a separate relay-brokered company record so they can be read by other
authorized community members without copying or changing the local run record.

The canonical head is kind `30649`, relay-signed and replaceable. Its d-tag is
`company:factory-run:<run-uuid>`. Commands are kind `47038`, member-signed and
brokered by the relay. Neither kind has an `h` tag. The run UUID is the id from
the native Factory record; it is never minted by the preview or pull request
pane. The first accepted command carries the immutable `runOwnerPubkey`. A run
owner may bind only their own key. A community owner/admin may bind the key
from the actual local run when acting on its behalf. A run owner or community
owner/admin may update the head.

The relay stores each accepted action and its replacement head in one
transaction. Every update carries the exact current `expectedHeadEventId` so a
stale write cannot overwrite a newer preview or pull request state. A command
without an expected head is create-only. The relay signs the resulting head
with the community relay identity.

## Head shape

Every head has `schemaVersion`, `runId`, `runOwnerPubkey`, `preview`,
`pullRequest`, and relay-authored `updatedAt`. UUIDs are canonical lowercase
strings. Pubkeys and event ids are 64 lowercase hex characters. Unknown fields
are rejected.

`preview` is a tagged value with exactly these states:

| State | Required data |
| --- | --- |
| `not_configured` | No saved command or local address |
| `not_started` | Saved development command and local address; a configured port and readiness check are optional for older records |
| `starting` | Saved configuration |
| `running` | Saved configuration and the actual preview URL |
| `failed` | Saved configuration and a non-empty failure reason; startup output is optional |
| `stopped` | Saved configuration |

The saved development command and local address are written only by an explicit
configure action. No value is inferred from mockup text. The relay accepts a
non-empty command up to 512 characters and a local address up to 2,048
characters. Local HTTP addresses must use a loopback host; other accepted
addresses use HTTPS and contain no credentials. The relay stores startup
output up to 4,096 bytes and rejects larger content.

Newer configure actions may also save `port` and `readiness` together. The port
must be from 1 through 65535 and match the local address. Readiness is either
`http_endpoint` with a loopback-relative path, or `output_message` with the
expected process output. Existing records without both fields remain readable.
Saving this configuration does not start a process.

Allowed transitions are `not_configured` to `not_started`, `not_started` to
`starting`, `starting` to `running`, `failed`, or `stopped`, `running` to
`failed` or `stopped`, and `failed` or `stopped` to `starting`. Reconfiguring a
stopped or failed preview returns it to `not_started`. There is no action that
claims a preview is running merely because configuration was saved.

`pullRequest` is either absent or contains the existing HTTPS URL, its positive
number parsed from a supported pull request path, a state, check results, and
optional review handoff. The supported states are `unknown`, `draft`, `open`,
`closed`, and `merged`. Each check result has a non-empty name up to 120
characters, a status of `unknown`, `queued`, `running`, `passed`, `failed`, or
`cancelled`, and an optional HTTPS details URL. There are at most 100 check
results. An empty check list means there are no recorded checks; it does not
mean checks passed. `reviewHandoff` is either null or plain text up to 4,000
characters, supplied by the authorized actor and never generated by the relay.
Production code must not synthesize any linked pull request values.

These fields are explicit member or agent attestations. The relay validates
their shape, scope, authority, and revision, but does not claim that an external
forge has verified them. `unknown` and absent data remain visibly unknown.
Unlinking clears the pull request from the head. Linking never creates a forge
pull request.

The linked record currently has no pull request title field, and a record does
not identify a reviewer or prove review delivery. The desktop does not invent a
title or claim that a review request was sent. Those details require a future
authorized provider integration and record fields.

Before accepting a new link, the relay requires an exact host in
`BUZZ_FACTORY_PR_HOSTS`, a comma-separated list of bare DNS hostnames. The
default is empty, which disables pull request linking. Wildcards, URL schemes,
and non-default ports are rejected. The desktop validates the URL shape for
user feedback; the relay's host allowlist is authoritative. No provider lookup
or external forge call is made when saving a link.

## Command actions

Kind `47038` accepts strict JSON with `schemaVersion`, `runId`, `action`, and
`runOwnerPubkey` when creating a head. Updates carry the exact
`expectedHeadEventId`:

- `configure_preview` supplies a command and loopback or HTTPS local address,
  with optional paired port and readiness fields. It saves configuration and
  leaves the state at `not_started`.
- `report_preview_state` supplies `starting`, `running`, `failed`, or `stopped`
  lifecycle data. A running state must include the actual reachable URL. A
  failed state must include the actual failure reason.
- `link_pull_request` supplies the existing URL, number, state, recorded check
  results, and optional review handoff.
- `unlink_pull_request` removes the current link.

The action signer must be the run owner or a community owner/admin. Channel-
scoped credentials cannot write these community-wide records. The relay obtains
role and signer identity from authenticated state, never from client-supplied
tags. Schema, d-tag, URL, bounds, transition, membership, authority, and
optimistic concurrency checks all run before the action and head are committed.

## Desktop boundary

The Preview and Review panes read this relay head for the selected real run.
Configuration can be saved because it is a real relay operation. This host has
no managed preview runtime that can guarantee process-tree containment and
cleanup, so Start, Retry, and Stop remain disabled with the runtime-unavailable
treatment. A record in `starting`, `running`, `failed`, or `stopped` is displayed
only from the relay-signed head and is not produced by this UI.

The approved batch 2 design includes the no-pull-request form and populated
Review pane. The pane displays only the saved URL, number, state, check results,
and review handoff. Provider-derived title, state refresh, check refresh, and
reviewer delivery are unavailable until an authorized provider API exists.
